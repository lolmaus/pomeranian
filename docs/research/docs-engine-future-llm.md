# Future LLM documentation feasibility

> Final decision (2026-09-22): the author selected VitePress with root
> `docs/site/` content and removed per-branch documentation versioning from scope.
> The comparison below preserves the evidence considered before that decision.
> Branch-version requirements, proposals, and acceptance checks are superseded,
> not deferred work. API/search and LLM findings remain relevant to the single
> current site. See the [current decision and scope](docs-engine-requirements.md).

Researched 2026-09-22 for the [confirmed requirements](docs-engine-requirements.md) and [prototype comparison](docs-engine-prototype-comparison.md). This covers future LLM-readable guide/API output, including branch-specific publishing. It does not add LLM implementation to the initial slice.

**Both engines have credible maintained-plugin paths for `llms.txt` and a complete Markdown bundle.** VitePress's plugin directly follows the external source root; Starlight's plugin follows the `docs` collection, so its loader location is not itself an LLM blocker. Neither plugin automatically proves correct links throughout a concatenated, versioned guide/API bundle. Generation order, collection membership, and link normalization are concrete integration obligations.

Evidence here is maintainer documentation and inspection of published package archives, without installation or execution. VitePress plugin source is pinned to its package's `gitHead`; Starlight plugin source is pinned to its 0.12.0 release-tag commit. Existing fixture success does not establish these plugins' runtime compatibility.

## VitePress: external sources and generated API

The plugin resolves its default `workDir` from `config.vitepress.srcDir`, so the tested `apps/docs` application consuming root `docs/site` has a direct configuration path. A pre-transform collects built `.md` modules within that directory; generation runs during the client `generateBundle` hook and skips the SSR build. It is not a recursive crawler of arbitrary repository Markdown or a conversion of finished page HTML. Sources: [configuration and lifecycle](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/plugin/plugin.ts), [Markdown collection](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/plugin/hooks/transform.ts).

**Inference for TypeDoc:** generate Markdown under the selected content tree, for example `docs/site/api`, before VitePress discovers/builds pages. Those actual pages can enter the same capture path as authored guides. Generating reference after the site's build cannot retroactively add it to that build's LLM bundle. A page that exists only as a component or unrelated HTML output is not established as included. This follows from the capture lifecycle above; combined TypeDoc/plugin execution remains untested.

The converter expands supported Markdown includes/code snippets, processes the plugin's LLM-specific tags, and strips HTML by default. Consequently, ordinary Markdown is the strongest path; HTML anchor tags or component-supplied content need inspection rather than an assumption that the LLM representation equals the rendered site. Source: [Markdown processor](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/plugin/hooks/markdown-processor.ts).

Publication control is separate from navigation. Global `ignoreFiles` and output-specific filters exist, but defaults also exclude the root `index.md`, blog patterns, and team content. The root index remains required when generating `llms.txt`, even when omitted as bundle content. **Implication:** if Pomeranian's home page contains meaningful instructions, explicitly review `excludeIndexPage` and exclusion presets. Keep the source-root boundary at `docs/site`; do not widen it to all `docs/` merely to find generated API. Sources: [defaults/lifecycle](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/plugin/plugin.ts), [filter implementation](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/utils/ignore.ts).

## Starlight: collection membership is the decisive condition

The plugin calls `getCollection('docs')`, selects default-language, non-draft entries, and processes those entries. It does not reopen the conventional `src/content/docs` directory. **Inference:** the external Astro glob collection already used by the fixture can feed it. The ordinary autogenerated-sidebar limitation does not by itself exclude those entries from LLM output. Source: [collection-based generator](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/generator.ts).

This condition matters for API generation. `starlight-typedoc` 0.23.1 writes Markdown beneath Astro's `srcDir/content/docs/<output>`, whereas the current fixture's glob reads only root `docs/site`. Using both unchanged would omit that generated API from the LLM collection. Source: [published TypeDoc generator](https://unpkg.com/starlight-typedoc@0.23.1/libs/typedoc.ts).

**Source-supported integration path:** use Astro's native glob loader with a repository-root base, an explicit pattern array selecting authored `docs/site` and the app-local generated API tree, and `generateId` to assign the intended guide/API IDs. This keeps true file paths and joins both inputs into one `docs` collection without copying authored content or building a custom loader subsystem. The LLM generator can then consume both sets through its existing collection lookup. This combined configuration and generation order remain untested. Emitting generic TypeDoc Markdown/frontmatter into `docs/site/api` is another possible path, not a necessary workaround. Source: [Astro glob loader configuration](https://docs.astro.build/en/reference/content-loader-reference/#glob-loader).

By default, the LLM plugin calls Astro `render(entry)`, renders the entry's `Content` with an Astro container, and converts that HTML to Markdown. It handles Expressive Code and Starlight tabs/file trees specifically. This uses rendered **entry content**, not a scrape of the complete built page and its navigation. `rawContent: true` returns `entry.body` instead, bypassing that conversion. UI-framework components require raw mode according to the maintainer; the agreed plain-Markdown/no-inline-React scope avoids that requirement. Sources: [rendering/conversion implementation](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/entryToSimpleMarkdown.ts), [raw-content documentation](https://delucis.github.io/starlight-llms-txt/configuration/#rawcontent).

For external files, Starlight documents `markdown.processedDirs` to extend its heading/asides processing beyond the standard loader's directories. A future configuration can include `../../docs/site`; the LLM plugin's rendered path would then receive that processed entry content. Astro 7 defaults to Sätteri; adding a Remark/Rehype recipe requires selecting the Unified processor explicitly. The LLM plugin's own internal Unified conversion is separate and does not itself require changing the website's Markdown processor. Sources: [Starlight processed directories](https://starlight.astro.build/reference/configuration/#processeddirs), [Astro Markdown processors](https://docs.astro.build/en/guides/markdown-content/#markdown-processors).

The plugin's `exclude` option filters **only `llms-small.txt`**. The full route passes no exclusion list, and configured custom sets use their own inclusion patterns. Therefore an excluded research tree should remain outside the `docs` collection, rather than relying on `exclude` or sidebar visibility. Non-draft collection membership defines the full bundle's scope. Sources: [full endpoint](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/llms-full.txt.ts), [small endpoint](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/llms-small.txt.ts), [custom-set endpoint](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/llms-custom.txt.ts).

## Version boundaries and accurate links

VitePress output URLs and per-page metadata incorporate `base` and an optional domain; page paths apply VitePress rewrites and normalize nested `index.md` output. Starlight requires Astro `site`, registers prerendered LLM endpoints, and constructs bundle links using `site` plus `base`. **Inference:** independently building each branch with its own source/API set and version base provides a credible way to keep each version's LLM artifacts separate. Neither plugin discovers branches or assembles a multi-version deployment. Sources: [VitePress page generation](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/generator/page-generator.ts), [VitePress rewrite handling](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/utils/vitepress-rewrites.ts), [Starlight index endpoint](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/llms.txt.ts).

That does **not** establish general rebasing of links inside each page's body:

- VitePress concatenates processed Markdown with per-page URL metadata. Its inspected processing pipeline has no general hyperlink-rebasing transform. Relative URLs moved into a root-level bundle, nested-index flattening, custom HTML anchors, and version-prefixed assets require checking. Its image helper uses a limited bundle-name map, not a general source-aware asset URL resolver. Sources: [full bundle](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/generator/llms-full-txt.ts), [preparation](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/plugin/hooks/prepare-markdown.ts), [image rewriting](https://github.com/okineadev/vitepress-plugin-llms/blob/0f3bbfa1f08ca28c8244b7e147368e5e8a8c34d9/src/markdown/remark-plugins/replace-image-urls.ts).
- Starlight's conversion pipeline does not generally absolutize rendered links, and raw mode simply retains the body. The fixture's already-broken authored `.md` URLs would not automatically become correct because this plugin was added. Even working page-relative site URLs need context when combined into a bundle. This is a source-based risk, not an observed installed-plugin failure. Source: [entry converter](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/entryToSimpleMarkdown.ts).

Neither inspected plugin exposes a per-entry URL-normalization callback in its public options. There are public engine extension paths if actual output requires correction:

1. **VitePress:** a small Vite `enforce: 'pre'` Markdown transform before the LLM capture plugin can retain the source `id`, resolve Markdown link/image nodes to intended published/versioned URLs, and pass normalized content onward. This also affects HTML processing; ordering and interaction with VitePress's own rewriting must be verified. A later Markdown-it rendering hook alone should not be assumed to alter the already captured source. This is a proposed recipe using public hooks, not a tested implementation. Source: [Vite 5 plugin API and ordering](https://v5.vite.dev/guide/api-plugin.html#plugin-ordering).
2. **Starlight:** an Astro Markdown processor plugin can normalize links while each entry's source context is available; the LLM plugin's default rendered-content path can inherit that result. `rawContent: true` bypasses the rendered result. This is likewise a proposed recipe, with Astro 7 processor configuration made explicit. Source: [Astro Markdown plugins](https://docs.astro.build/en/guides/markdown-content/#markdown-processor-plugins).
3. **If normalization must affect only LLM output:** use a small owned generator with page/source context, through a documented VitePress build hook or Astro static endpoint. Neither plugin needs to be forked merely to make that architecture possible, but its implementation is additional project-owned work. Starlight's internal converter is not exported as a supported package subpath. Sources: [VitePress build hook](https://vuejs.github.io/vitepress/v1/reference/site-config#buildend), [Astro static endpoints](https://docs.astro.build/en/guides/endpoints/#static-file-endpoints), [Starlight package exports](https://github.com/delucis/starlight-llms-txt/blob/776a90165beecf779542d52b67c8290af728a150/packages/starlight-llms-txt/package.json).

Normalization should operate on parsed links with each source page's route and version identity **before concatenation**. A generic regex replacement on the finished full bundle cannot reliably recover that context or distinguish code examples from links. This is an engineering recommendation, not a promise that the eventual recipe will be trivial.

## Bounded future acceptance

When adding LLM output, test a small representative set rather than rebuilding the entire future system in advance:

1. Generate one API page from the branch's actual source before collection/page discovery; assert a distinctive signature and one authored guide sentence occur in the full bundle.
2. Include a nested guide, an API symbol link/anchor, a multiline TypeScript example, and a colocated image. Follow generated index links and inspect bundle/per-page links at a non-root version base. Verify signatures, code indentation, and meaningful prose survive conversion.
3. Assert an excluded research sentinel is absent from every emitted LLM output. Check a meaningful home-page paragraph deliberately, because VitePress's default index exclusion can otherwise omit it.
4. Build two branch revisions with different signatures; verify each LLM bundle contains only its branch's content and all listed URLs preserve that version prefix. Publish both artifacts without overwriting one another.
5. Record any owned normalizer, collection composition, or generator and test its narrow contract. Reassess if this grows beyond the accepted small maintained recipe.

No runtime integration or fork is justified by this report alone. Current source establishes plausible paths and identifies where future validation matters; it does not establish the complete TypeDoc/search/LLM/versioning pipeline for either candidate.
