Verified: 2026-09-22. Isolated comparison with [the VitePress fixture](docs-engine-minimal-verification.md), using the same repository-root `docs/site/` publication boundary and `apps/docs/` application layout. This is compatibility evidence, not the real docs bootstrap or an engine decision.

## Result

**Astro's native external `glob()` loader plus Starlight's `docsSchema()` builds and serves the three plain-Markdown pages without copying, symlinks, or framework resolution aliases.** A direct app dependency on Sharp was needed for the colocated SVG image to build. Root research content remained excluded, and editing, adding, and deleting external Markdown worked without restarting the dev server.

Two separate limitations were observed:

- Authored relative `.md` links were emitted unchanged and returned HTTP 404 when followed. Canonical site routes worked. This is a Markdown-file-link portability gap, not a failure to render external content; Starlight documents site-URL links. A rewrite integration was not added.
- Starlight's ordinary `autogenerate: { directory: 'guide' }` sidebar configuration produced no guide links with the external glob collection. Inspection of the installed navigation implementation confirms it derives directory membership by removing the fixed `src/content/docs/` prefix from each entry's `filePath`. External `../../docs/site/...` paths do not match. **An explicit sidebar subsequently passed**, matching the VitePress fixture's hand-written navigation: both rendered guide links returned HTTP 200 with the expected page content. The empty autogenerated group is a separate convenience limitation, not a blocker for minimal explicit navigation. Its configuration is preserved as a baseline.

The edit-source URL worked after configuring its base for the application directory inside the monorepo. Last-updated Git dates were not proved because this temporary fixture has no Git history. Browser hydration, browser-visible HMR, and interactive search were not tested.

## Configuration tested

The workspace contains `apps/*`. `apps/docs/package.json` has exact dependencies on the Astro, Starlight, Markdown Remark, and Sharp versions above, with scripts `astro build`, `astro dev`, and `astro preview`.

`apps/docs/astro.config.mjs`:

```js
import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';

export default defineConfig({
  integrations: [
    starlight({
      title: 'Location verification',
      sidebar: [
        {
          label: 'Guide',
          items: [
            { label: 'Guide start', link: '/guide/start/' },
            { label: 'Nested next', link: '/guide/nested/next/' }
          ]
        }
      ],
      editLink: {
        baseUrl: 'https://github.com/example/fixture/edit/main/apps/docs/'
      },
      lastUpdated: true
    })
  ]
});
```

This final explicit sidebar was built and its emitted links were followed through preview HTTP. `apps/docs/baseline-astro.config.mjs` preserves the earlier `items: [{ autogenerate: { directory: 'guide' } }]` configuration whose group is empty. No plugin or loader modification was needed for explicit navigation.

`apps/docs/src/content.config.ts`:

```ts
import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { i18nLoader } from '@astrojs/starlight/loaders';
import { docsSchema, i18nSchema } from '@astrojs/starlight/schema';

export const collections = {
  docs: defineCollection({
    loader: glob({ base: '../../docs/site', pattern: '**/*.md' }),
    schema: docsSchema()
  }),
  i18n: defineCollection({ loader: i18nLoader(), schema: i18nSchema() })
};
```

Astro documents `glob()` as supporting files outside the application tree. Starlight's own `docsLoader()` still wraps that loader around its conventional `src/content/docs` location and accepts `generateId`, not a configurable content base. Replacing it with Astro's loader is a supported Astro API but does not remove Starlight's other fixed-location assumptions. The fixture's simple glob also does not reproduce Starlight's underscore-filename exclusion or every supported extension. Sources: [Astro loader API](https://docs.astro.build/en/reference/content-loader-reference/#glob-loader), [Starlight loader source](https://github.com/withastro/starlight/blob/main/packages/starlight/src/loaders.ts), [Starlight collection helper source](https://github.com/withastro/starlight/blob/main/packages/starlight/src/utils/collection.ts). The corresponding installed `dist/loaders.js`, `dist/utils/collection.js`, and `dist/utils/navigation.js` were inspected at version 0.42.2.

Every Markdown page supplies required `title` frontmatter, for example:

```md
---
title: Guide start
---

EXTERNAL_CONTENT_INITIAL_20260922

[Home](../index.md)

[Next](./nested/next.md)

![Fixture icon](./icon.svg)
```

The same tree includes `index.md`, `guide/nested/next.md`, `guide/icon.svg`, and an excluded `docs/research/internal.md` sentinel. Only `docs/site/**/*.md` is loaded. No MDX or React integration was used. Sources: [Starlight frontmatter](https://starlight.astro.build/reference/frontmatter/), [Starlight Markdown authoring](https://starlight.astro.build/guides/authoring-content/).

## Failures, corrections, and HTTP observations

The first attempt used an obsolete sidebar shape with `label` alongside `autogenerate`; Starlight rejected it with an explicit v0.39 migration hint. Updating to the current grouped `items` schema fixed that configuration error. It did not fix the external-path autogenerated-sidebar behavior described above.

The next production build rendered all pages, then failed while optimizing the SVG with `MissingSharp`. Adding direct `sharp: '0.35.4'` to the app fixed this; no content relocation or custom image service was used. The first successful build completed in 3.71 seconds and the final explicit-sidebar build in 3.70 seconds. These timings are not controlled benchmarks.

| Check | Observed outcome |
| --- | --- |
| Production output | Home, `/guide/start/`, and `/guide/nested/next/` generated and returned HTTP 200 with the expected content. |
| Selected publication | The research sentinel was absent from all generated files. |
| Relative SVG | Production emitted an optimized `/_astro/icon…svg`; following its rendered `src` returned HTTP 200 SVG. Dev used its image endpoint and also returned HTTP 200 SVG. |
| Authored `.md` links | All four links failed in both preview and dev; exact failures below. |
| Explicit guide sidebar, final configuration | Both guide hrefs were present and followed from all three preview pages; every request returned HTTP 200 with expected content. |
| Autogenerated guide sidebar, baseline configuration | No `/guide/start` or `/guide/nested/next` hrefs were present in the built guide HTML despite both routes existing. |
| Edit-source URL | After correcting the application-root base, both preview and dev emitted `https://github.com/example/fixture/edit/main/docs/site/guide/start.md`. The external service was not contacted. |
| Last-updated date | No `<time>` element appeared; no Git history exists in this fixture. This is not proof of correct Git-date behavior. |
| Cold dev | Generated `.astro`, `node_modules/.astro`, and `node_modules/.vite` caches were removed before the final foreground dev startup. Content loaded without dependency-resolution errors. |
| Edit external page | Same process served the changed marker through the canonical page URL. |
| Add external page | Same process eventually served the added page; the probe allowed the watcher/content collection to refresh. |
| Delete external page | Same process eventually returned HTTP 404 with the removed marker absent. |
| Cleanup | Original content restored; foreground preview and dev processes terminated. |

Actual authored-link destinations, resolved from the served page URLs:

| Authored href | Browser-resolved destination | Result |
| --- | --- | --- |
| `./guide/start.md` from `/` | `/guide/start.md` | 404 |
| `../index.md` from `/guide/start/` | `/guide/index.md` | 404 |
| `./nested/next.md` from `/guide/start/` | `/guide/start/nested/next.md` | 404 |
| `../start.md#guide-start` from `/guide/nested/next/` | `/guide/nested/start.md#guide-start` | 404 |

Starlight's documented site URLs avoid this `.md`/directory-route mismatch. Adopting those links in Markdown would weaken the desired GitHub file-link behavior; a maintained rewrite rule would be additional work. No rewrite plugin or canonical-link authoring variant was implemented during this check.

Initially the edit-link base ended at `/edit/main/`. Starlight appends the entry's `../../docs/site/...` path, so URL normalization removed `edit/main` and produced a wrong target. Setting the base to `/edit/main/apps/docs/` fixed it using ordinary configuration. This initial failure is not an unavoidable loader limitation.

Build/dev logs contain warnings for the absent/empty optional i18n collection and missing custom 404 entry. Builds also skip sitemap generation without a production `site` URL. Requests intentionally probing broken or deleted routes produce normal unmatched-route warnings. No dependency-optimizer resolution warnings were observed in the final cold dev log. Starlight incidentally built its default Pagefind index; search interactions and guide/API search coverage were not evaluated.

Astro 7 detects agent execution and can background its servers automatically. Early probe termination stopped the launcher, leaving fixture daemons running; this was detected, those exact daemons were terminated, and final evidence was rerun using the documented `--ignore-lock` foreground mode. The preserved probe uses that flag and owns server cleanup. Source: [Astro CLI](https://docs.astro.build/en/reference/cli-reference/#astro-dev).

## Reproduction and remaining limits

Preserve the fixture root package manifest, workspace YAML, lockfile, `registry-metadata.json`, `apps/docs/package.json`, `apps/docs/astro.config.mjs`, `apps/docs/baseline-astro.config.mjs`, `apps/docs/tsconfig.json`, `apps/docs/src/content.config.ts`, authored `docs/` files, and `verify-runtime.py`. `runtime-results-baseline.json` captures the final baseline cold-dev/preview observations; `runtime-results-preview.json` captures the final explicit-sidebar production/preview check. The final `dev.log` and `preview.log` are also retained. Dependency stores, `node_modules`, `.astro`, generated output, and state/cache directories are disposable.

The probe locates the fixture relative to its own file and accepts `NODE_BINARY`; it records expected compatibility failures rather than presenting them as an all-pass suite. In the fixture, with Node 24.21.0 and pnpm 11.27.1 active:

```sh
ASTRO_TELEMETRY_DISABLED=1 pnpm install --reporter append-only --fetch-retries 0 --fetch-timeout 15000
ASTRO_TELEMETRY_DISABLED=1 pnpm --filter starlight-fixture run build
ASTRO_TELEMETRY_DISABLED=1 python3 verify-runtime.py
```

For the narrow navigation check alone, run `python3 verify-runtime.py --preview-only` after the build. The full probe now expects the explicit sidebar. The sidebar-only follow-up did not repeat the already completed cold-dev watch checks; their evidence is from the baseline configuration using the same content loader and dependencies.

The actual run used the already available binaries under `/tmp/pomeranian-bootstrap-fnm/node-versions/v24.21.0/installation/` explicitly and a fixture-local `XDG_STATE_HOME`; temporary workspace store/cache paths must be adjusted if moving the fixture. The probe starts local-only preview on port 43279 and dev on 43280.

The installed Starlight collection helper still documents fixed content-location assumptions for Git dates and language inference. Its navigation implementation adds the observed autogenerated-sidebar consequence. English-only use removes the multilingual requirement but does not establish that all Starlight features or plugins understand this replacement loader. Last-updated production metadata needs a real Git-history fixture if adopted.

This report does not test actual workspace Turbo inputs, CI packaging, deployment, browser hydration/HMR, accessibility interactions, TypeDoc, API/search integration, LLM exports, or branch version switching. It introduces no public demo requirement. The useful comparison is narrower: external source rendering and watching work, while native `.md` link rewriting and fixed-content-directory conveniences differ from VitePress.
